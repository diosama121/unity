💣 暗雷一：L2跟车层的“磕头式追尾” (永远停不下来的车)
病因源头：
在 SubsumptionEngine.cs 的 ComputeL2 (跟车避障层) 中，你写了这么一句：

C#
float targetSpd = Mathf.Lerp(0f, s.frontSpeed, distRatio);
targetSpd = Mathf.Max(targetSpd, 1f); // 最低 1m/s，不跟停
致命后果：
这句 最低 1m/s，不跟停 是一个巨大的逻辑漏洞。当且仅当红绿灯（L1）未触发时，如果前车停死在路边，你的车会进入 L2 跟车。但因为它最低只能减速到 1m/s，它会持续以 1m/s 的速度往前蠕动，直到触发 L3 (AEB 紧急制动，距离 < 3.5m)。
触发 AEB 后，车子猛烈急刹停下；一旦停下，距离可能大于 3.5m，控制权又交还给 L2；L2 发现前车，又输出 1m/s 往前蠕动……
结果就是你的车会在前车屁股后面疯狂“磕头”（急刹-蠕动-急刹-蠕动），永远无法安稳停下。

解药：
彻底删掉那个 1f 的下限，允许 L2 随前车完全刹停：

C#
float targetSpd = Mathf.Lerp(0f, s.frontSpeed, distRatio);
// 删除 targetSpd = Mathf.Max(targetSpd, 1f); 
💣 暗雷二：断网导致的“永久高位截瘫”
病因源头：
在 ROS2BridgeV2.cs 的 Update() 方法中，超时和断连的处理逻辑存在严重的执行顺序漏洞。

C#
// 2. 超时/断连 -> 移交本地 AI
if (useRosControl && (!isConnected || isTimeout)) { ... }

// 如果没连接，直接 return (截断了后续所有代码！)
if (!isConnected) return; 

// 5. 解除 AEB 的逻辑在这里...
if (_aebActive) { _specialSituations.TriggerExternalAEB(false); ... }
致命后果：
假设 ROS2 传来了 BRAKING 指令，主车的 AEB 被激活。此时突然网络波动或者 ROS2 节点崩溃，isConnected 变为 false。
下一帧进入 Update，代码走到 if (!isConnected) return; 就直接退出了！下方用来解除 AEB TriggerExternalAEB(false) 的代码永远不会被执行。
结果你的主车会被死死锁在原地（刹车焊死），直到你重启游戏。

解药：
在断线降级逻辑中，强制清空 AEB 状态：

C#
        // 2. 超时/断连 -> 安全降级
        bool isTimeout = (Time.time - lastReceiveTime > rosTimeout);
        if (!isConnected || isTimeout)
        {
            if (useRosControl)
            {
                Debug.LogWarning("[ROS2Bridge] AEB连接超时！交还本地AI控制...");
                useRosControl = false;
                rosLinearVelocity = 0f;
                rosAngularVelocity = 0f;
                if (_autoDrive != null) { _autoDrive.enabled = true; _autoDrive.ResetNavigation(); }
            }

            // ★ 修复：断网时必须强行释放本地的被锁死的AEB状态
            if (_aebActive) 
            {
                if (_specialSituations != null) _specialSituations.TriggerExternalAEB(false);
                _aebActive = false;
            }
        }
        if (!isConnected) return;

💣 暗雷四：A* 寻路的“重叠计费” (喜欢绕远路的导航)
病因源头：
在 PathPlanner.cs 的 PlanEdgePath 里，你在计算边代价（EdgeCost）时，对车道长度进行了重复叠加：

C#
float edgeCost = laneLen + connLen + nextLen;
float tentativeG = currentNode.GCost + edgeCost;
致命后果：
假设路径是：车道A -> 路口1 -> 车道B -> 路口2 -> 车道C。
当你从 A 算到 B 时，G 包含了 A长 + 路口1长 + B长。
当你从 B 算到 C 时，G 等于之前的 G 加上 B长 + 路口2长 + C长。
B 的长度被算了两遍！ 如果你经过 5 个十字路口，中间车道的长度会被成倍放大。这会导致 A* 算法极度“厌恶”穿过路口，宁愿让车去绕外环那些单条巨长的远路，也不愿意走近道。

解药：
节点转移的代价只算“当前段”，不预支下一段（因为下一段在下一次遍历时自然会算）：

C#
// ★ 修复：边代价只算离开当前车道并穿过连接器的长度，到达 nextLane 的端点即可
float edgeCost = laneLen + connLen;

💣 新雷一：ROS2 激光雷达的点云“空间坍缩”（会导致 Python 端彻底瞎掉）
问题位置： ROS2BridgeV2.cs 的 GenerateLidarPoints()。
病因：
你在做射线检测时，只有当 Physics.Raycast 扫到东西时，才把 x, y, z 塞进 points 列表。
如果一根射线打向天空或者没有命中，你什么都没加！
致命后果：
假设你的 LiDAR 有 11 根射线。第 0 根没命中，第 1 根命中了。
发给 Python 端的数组长度变短了，Python 拿到这串数字，会默认这是第 0 根射线的数据！这会导致整个雷达扫描画面在 Python 端发生严重的“角度偏移和数据错位”，ROS2 算出来的 TTC（碰撞时间）和避障方向完全是歪的。
解药： 必须保证数组长度恒定。没命中时，要塞入一个最大距离的点：

C#
if (Physics.Raycast(origin, dir, out RaycastHit hit, lidarMaxRange, lidarLayerMask)) {
    Vector3 localHit = _carTransform.InverseTransformPoint(hit.point);
    points.Add(localHit.x); points.Add(localHit.y); points.Add(localHit.z);
} else {
    // ★ 修复：未命中时，必须填充最大距离的假点，保住数组的索引顺序！
    Vector3 maxPoint = _carTransform.InverseTransformPoint(origin + dir * lidarMaxRange);
    points.Add(maxPoint.x); points.Add(maxPoint.y); points.Add(maxPoint.z);
}
💣 新雷二：ROS2 接管权与本地玩家控制权的“精神分裂”
问题位置： ROS2BridgeV2.cs 中的 FindMainCar() 和 Update()。
病因：
在 FindMainCar 里，如果没有主车，你会强行把一辆 NPC 变成主车：main.isPlayerControlled = true;。
这会触发 SimpleAutoDrive 的逻辑：它一看到 isPlayerControlled 是 true，就会立刻设置 carController.manualControl = true，把自己变成键盘遥控的玩具车。
紧接着，在同一帧的 ROS2BridgeV2.Update 下方，你为了让 ROS2 下发指令，又强行写了 _carController.manualControl = false;。
致命后果：
这两个脚本每一帧都在疯狂互殴。底盘 manualControl 状态每半毫秒切换一次，ROS2 发过来的油门指令会被 Unity 本地的键盘输入（哪怕是 0）不断覆盖，车子会剧烈抽搐甚至失控。
解药： 在 FindMainCar 里，绝对不要去动 isPlayerControlled。如果你想让 ROS2 选一辆车接管，只需要给 SimpleAutoDrive 新加一个专门的布尔值（比如 isROSControlled），或者直接禁用 SimpleAutoDrive 即可。
